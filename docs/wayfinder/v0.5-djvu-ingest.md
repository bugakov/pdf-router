# Wayfinder map — v0.5 djvu ingest

## Destination

djvu works end-to-end: `convert("книга.djvu")` emits the same quality LLM/RAG
material as PDF/DOCX (md/chunks/json renderers, sidecar images), verified on
real djvu from the vbrdb corpus (33 files in
`~/vbrdb/orchestrator/uploads/`) and committed. The integration strategy — **upstream conversion** (caller
converts djvu→PDF first), **in-router conversion** (ddjvu inside the djvu
inspector), or **native render + PageSource seam** — is *decided on evidence,
not assumed*: it is the map's root decision ticket and feeds ADR-0004.

**STATUS: REACHED (2026-09-13)** — strategy C landed per ADR-0004; all
tickets closed; sidecar images for djvu are a deliberate no-op (TKT-DJV-06:
a djvu page is itself a page-background scan). Commit pending.

## Notes

- Domain: `pdf-router` Python project (uv, Python ≥ 3.12); sole consumers are
  local RAG indexing pipelines. Ethos: "ultra-minimal, deterministic,
  deploy-anywhere" (`pyproject.toml` description).
- Skills per session: `grilling` (one question at a time), `domain-modeling`
  (when a term graduates), `research` subagent (outside-knowledge tickets).
- Reply style: short, plain language (user has ADHD) — no jargon walls,
  compact question packages only.
- Standing preferences carried from the v0.4 map (do not re-litigate):
  - No heavy AI parsers (docling, unstructured, ...) — violate minimal
    resources.
  - Images as sidecar paths, not base64 in IR (TKT-RT-08).
  - Flat functions; one file over many; tunables in TOML config.
  - The format dispatch seam is locked (commit 57cfa1f): magic-byte detect →
    Inspector registry (`src/pdf_router/formats.py`); adding a format = one
    enum member + one magic branch + one registry entry.
  - User commits via `gaa && forge commit && gp` — leave changes uncommitted.
  - `uv run python` / `uv run pytest` (bare `python` not in PATH); never two
    pytest runs in parallel.
- **Deliberately NOT carried over:** ADR-0003's "no external binaries"
  ruling was docx-specific (LibreOffice: hundreds of MB + structure
  flattening). Whether an external binary (ddjvu — small, deterministic,
  already installed at `/usr/bin`) may enter the *djvu* dependency path is
  part of the open strategy decision (TKT-DJV-02). Do not pre-rule either
  way.
- Empirical baseline (probed 2026-09-12, refined by TKT-DJV-01 research):
  **33 djvu** under `/home/scanum/vbrdb/orchestrator/uploads/` (21 visible +
  12 `._`-prefixed; 0 probe failures); `ddjvu` + `djvused` installed; the
  toolchain is proven by the user's reference pipeline
  `~/vbrdb/src/preprocessing/djvu_to_pdf.py` (ddjvu → PyMuPDF/pyvips
  compression). Registry `original_djvu_path` values are stale (files now
  live in `uploads/`). Key corpus facts: median 209 pages / 7.9 MB;
  JB2 stencils everywhere + IW44 backgrounds almost everywhere; hidden
  text layers in **3/33 files only** (but high quality); ddjvu's PDF
  output is **image-only** (source-verified) — detail in
  [`research/djvu-tools.md`](research/djvu-tools.md).
- Locked seam facts any strategy must face: the OCR pass signature is
  `(pdf_path, page_number)` and image extraction goes through pymupdf
  (`src/pdf_router/core.py`) — the PDF-shaped downstream is the constraint
  strategy C (PageSource seam, architecture-report candidate 4) would
  generalize and strategies A/B would sidestep.
- djvu is a scan format by nature: no structure to flatten (unlike docx —
  the ADR-0003 anti-conversion arguments mostly do not transfer), and the
  pipeline's OCR path is the natural destination for its pages. A hidden
  text layer (TXTz/TXTa) may exist in corpus files — prevalence and quality
  is TKT-DJV-01 evidence.

- [TKT-DJV-01 — Research: djvu toolchain & corpus survey](tickets/TKT-DJV-01-djvu-toolchain-corpus-research.md)
  — **text layers in 3/33 files (9.1%, high quality but rare); ddjvu PDF
  output is image-only (verified in djvulibre source); pymupdf cannot open
  djvu; python-djvulibre is sdist-only and needs `cython<3` on Python 3.12;
  5 golden anchors shortlisted.** Evidence:
  [research/djvu-tools.md](research/djvu-tools.md).
- [TKT-DJV-02 — Integration strategy: upstream conversion vs in-router
  conversion vs native render](tickets/TKT-DJV-02-djvu-integration-strategy.md)
  — **strategy C (native render + PageSource seam) via the `ddjvu`
  subprocess per page — zero new Python dependencies; python-djvulibre
  rejected (cython<3 pin, sdist-only, dormant); A rejected (breaks the
  embed promise); B rejected (whole-file temp PDF, loses text layers,
  double encoding).** The seam is the raster-acquisition point in the OCR
  engines — graduated into TKT-DJV-11.
- [TKT-DJV-12 — Research: ddjvu per-page render cost baseline](tickets/TKT-DJV-12-ddjvu-per-page-render-baseline.md)
  — **verdict (a): per-page on demand is fine — median 162 ms/page
  (spawn + decode + ppm→numpy), +10–14 MB per raster, no whole-file
  re-decode penalty (552-pp file flat across pages 1/276/552); a 209-page
  book ≈ 17 s render at workers=2 vs 42–70 min OCR — rendering is noise
  next to OCR. In-memory bytes beats temp files.** Evidence:
  [research/djvu-tools.md](research/djvu-tools.md) (TKT-DJV-12 section).
- [TKT-DJV-03 — Page semantics for djvu in the IR](tickets/TKT-DJV-03-djvu-page-semantics.md)
  — **0-based physical pages like pdf (per-page keying; docx page-0
  precedent does not carry over); djvu inspector = "pdf-inspector that
  knows needs_ocr per page" (layer → native + quality gate, layerless →
  `inspector_needs_ocr`); counters unchanged; `pdf_type` always
  `"scanned"` (confidence 1.0); tables/columns lists empty; text pass
  gates on `source_format ∈ {pdf, djvu}`.** IR bump deferred to
  TKT-DJV-04.
- [TKT-DJV-04 — Hidden text layer policy](tickets/TKT-DJV-04-djvu-hidden-text-layer-policy.md)
  — **new `SrcTool.DJVU_TEXT_LAYER` (reuse would lie); honesty via three
  existing carriers, zero new fields (`source_format="djvu"`, per-page
  `src_tool`, `pages_needing_ocr` excludes layer pages); `blocks=[]`
  always; IR bumped 0.3 → 0.4 (old readers crash on the new enum value —
  the bump makes that visible); layer is first-class under C, read
  straight from the djvu file.** Native-vs-re-OCR and the failed-gate
  fallback were already fixed by TKT-DJV-03.
- [TKT-DJV-06 — Images & sidecar semantics for djvu](tickets/TKT-DJV-06-djvu-images-sidecar.md)
  — **`page.images = []` always: the image pass does not run for djvu —
  the same rule scanned pdf pages already follow (≥80%-of-page images
  are filtered as page-background, `extract_images.py:127`); no page
  strips, no djvudump chunks; raster/vector flags are a documented
  no-op; purity invariant holds. Side effect: TKT-DJV-11 loses its
  image-pass consumer — OCR is the only raster consumer.**
- [TKT-DJV-05 — Conversion artifact lifecycle & determinism](tickets/TKT-DJV-05-djvu-conversion-artifact-lifecycle.md)
  — **no temp files, no cache: page raster in memory only (closes the
  fork TKT-DJV-12 left open); ddjvu failure = per-page error, run
  continues; one subprocess per page, no shared state.**
- [TKT-DJV-07 — CLI --info and exit codes for djvu](tickets/TKT-DJV-07-djvu-cli-info-exit-codes.md)
  — **`djvu_info()` modeled on `docx_info` (same-parser-no-drift):
  source_format/page_count/pdf_type/pages-with-layer JSON, exit 0;
  exit-code table unchanged; the "not supported yet" refusal branch
  stays as the template for future formats; --info is djvused-only
  (cheap).**
- [TKT-DJV-11 — PageSource seam: format-aware raster acquisition](tickets/TKT-DJV-11-pagesource-seam-raster-acquisition.md)
  — **one function in `rasterize.py` ("page N's raster"): pdf → pymupdf
  (byte-identical), djvu → ddjvu PPM→stdout; engines keep signatures.
  rapidocr gets numpy, tesseract/deepseek get PNG, glm gets a wrapped
  pdf_inspector_ocr honestly refuses (PDF-only). ddjvu failure =
  per-page error.**
- [TKT-DJV-08 — Quality bar: golden anchors on the vbrdb corpus](tickets/TKT-DJV-08-djvu-quality-bar-golden-anchors.md)
  — **4 anchors (small/typical/text-layer/largest); fast tier = tiny
  committed fixtures + stubbed OCR (gates, counters, seam, purity,
  lying extensions); slow tier = real OCR on the small anchor
  (determinism) + text anchor (layer → DJVU_TEXT_LAYER, no OCR);
  error-honesty and purity invariants in both tiers.**
- [TKT-DJV-09 — ADR-0004: djvu ingest strategy](tickets/TKT-DJV-09-adr-0004-djvu-ingest.md)
  — **[docs/adr/0004-djvu-ingest.md](../adr/0004-djvu-ingest.md) written
  and Accepted: strategy C + ddjvu subprocess, all sub-decisions locked,
  alternatives with reasons, IR 0.4 bump, implementation checklist.**
- [TKT-DJV-10 — Implement the djvu path end-to-end + docs](tickets/TKT-DJV-10-implement-djvu-end-to-end.md)
  — **done, destination reached. IR 0.4 landed (`DJVU_TEXT_LAYER` +

## Out of scope

- **vbrdb orchestrator integration** — the upstream consumer's own pipeline
  (incl. its smart-compression step) stays as is; this effort is
  router-scoped. Revisit as a separate effort if wanted.
- **Other formats** (epub, html, xlsx, ...) — beyond djvu.
- **Heavy AI document parsers** (docling, unstructured, ...) — carried from
  v0.4; violate the minimal-resources constraint.
- **DocLang as IR/renderer** — ruled out by `docs/adr/0002-doclang-not-as-ir.md`.
